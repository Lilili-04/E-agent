# Agent Note: 环境政策法规知识问答

Status: proposed

[English](2026-09-25-environment-policy-qa.md) | 中文

## Problem

项目需要第一个环境领域 Agent，用于回答国家级环境法律、法规、标准、规划和政策文件相关问题。当前 Corpus 位于 Harness 仓库之外，包含 494 份国家级 `full.md` 文档。这些文档混合了正式法规、规划、通知、历史版本、征求意见稿、附件和 OCR 结果。单纯依赖提示词或只使用向量 RAG，无法稳定选择具有法律适用性的版本、保留数字和否定词，也无法生成可复核的证据。

## Proposal

将该能力作为可选的 Harness 插件组合实现。原始文档继续放在 Harness 仓库之外，原始资料根目录通过插件配置显式传入。插件负责离线导入和索引、查询服务、面向模型的工具以及环境法规 Agent preset。保持 Agent Loop 不变。

### 第一版范围

第一版只纳入国家级资料，支持文档发现、条款或段落检索、证据展示，以及在来源元数据已核验时按日期筛选。系统不能声称每份文件当前有效，也不能根据文件名或模型常识自动确认法律效力。省级资料、完整法律本体、全自动条款沿革、图数据库部署和自主法律意见不属于第一版。

### 原始资料与生成数据边界

`policy_md/national` 是原始资料源。导入器读取 `full.md`、现有解析元数据和可选 PDF，不将这些文件复制到 Git。SQLite 数据库、全文索引、向量、导入报告和缓存都是可重建产物，不提交到 Git。配置的资料根目录不存在或不可读时，插件应明确失败。

### 导入和文档模型

导入器建立 `source_document`、`regulation`、`regulation_version`、`content_unit`、`version_relation` 和 `review_record` 六类逻辑记录。来源文件不能自动等同于法规版本：多个来源可能重复同一版本，同一部法规也可能包含多个历史版本。可检索单元可以是条、款、项、段落、章节、表格或附件，因为政策文件不一定使用条款编号。

每个来源保存路径、内容哈希、解析时间、候选标题、文件类型和解析质量状态。每个版本分别保存发布日期、生效起始日期、生效终止日期、导入时间、解析时间和审核时间。缺少日期时保留未知；终止日期为空只表示“没有记录到终止日期”，不表示“已经确认今天有效”。状态至少区分已核验有效、已核验失效、草案、已废止、已替代和未确定。

解析器保留原文行号范围、章节路径、条款或段落标记和原始文本。对于发布令或通知位于正文标题之前、只有附件、包含表格或存在 OCR 异常的文件，解析器不能强行套用同一种结构，也不能凭空补全文本。导入报告应确定性地列出标题冲突、过短文件、重复哈希、缺失元数据和低置信度结构解析。

### description 摘要生成

按“文档版本”生成一条 description，而不是为法规实体永久保存一条摘要。摘要用于文档列表和文档级检索，长度建议为 80～200 字，保存来源哈希、提示词版本、模型标识、生成时间和审核状态。摘要不能声称当前有效、全国适用或原文没有的事实；来源变化后，旧摘要标记为过期。

摘要不是法律证据。回答证据只能来自条款、章节或段落原文以及已核验的元数据。现有 `policy_prompt.md` 可以作为初始抽取规范；即使摘要模型输出不完整，导入器仍必须保留完整 Markdown 原文。

### 索引和检索顺序

第一版使用 SQLite 保存元数据，并建立可重建的全文索引。为标题、别名、文号、标准编号、条款号和日期建立精确索引。中文全文检索必须在代表性评测集上验证；对于法规名称、数字、日期和法律情态词，可以同时使用字符或短语匹配。

每个问题先规范化为可选的意图、日期或日期范围、地域、文件类型、法规名称、主体、行为、条款号和版本比较请求。只要条件明确，就在语义排序前应用约束：

1. 解析明确的法规名称、文号、条款号和日期。
2. 按地域、文件类型、状态和已核验的时间事实过滤候选版本。
3. 使用精确匹配和全文检索召回内容单元。
4. 对口语化或模糊问题增加 description 级匹配。
5. 在评测证明需要时，增加向量候选作为补充召回。
6. 按字段命中、结构位置、来源质量和时间兼容性重排。
7. 返回有上限的证据包，包括原文、来源位置、版本日期、状态和匹配原因。

向量检索要等评测集证明词法检索遗漏了大量改写问题后再引入。向量索引可以提高召回率，但不能判断法规效力、覆盖精确数字或替代条款号和日期检查。图数据库同样后置；在需要复杂沿革遍历之前，版本关系表已经足够。

### Harness 接入

插件提供类似 `search`、`getEvidence`、`findVersions` 和 `resolveTemporalStatus` 的知识服务操作。独立的面向模型工具通过 `ctx.tools` 注册，返回包含文档、版本、内容单元、证据和不确定性字段的规范 JSON。第二个证据工具可以根据搜索结果读取完整原文。工具输出有大小上限并响应取消信号，持久化工具调用可以由 Session 日志重建。

组合配置通过 `ctx.systemPrompt` 增加法规问答规则，要求回答先证据后结论，区分发布日期和生效日期，明确不确定性，并引用返回的来源。Agent preset 组合法规工具和提示词，不改变标准 Agent。现有 Web 搜索工具可以辅助核对外部官方来源，但外部结果必须标记为未入库或未审核，不能静默替换本地已核验记录。

### 回答契约

回答包含直接结论、选定的文档版本、生效时间解释、条款或章节位置、简短原文摘录、来源路径或官方 URL，以及元数据不完整时的不确定性说明。模型只能依据证据包生成实质结论。没有已核验证据时，工具结果应明确表示系统无法确认，并可以列出最接近的候选项。

### 交付阶段

1. 为全部 494 份国家级文档生成盘点和质量报告。
2. 选取 50～100 份，覆盖法律、法规、规划、标准、通知、草案、附件和历史版本，完成样本导入。
3. 实现 SQLite 数据模型、确定性 Markdown 解析器、description 生成器和精确/全文检索。
4. 完成查询服务和证据包测试。
5. 接入 Harness 工具、系统提示词和可选择的 Agent preset。
6. 建立 80～150 个评测问题，覆盖条款定位、口语主题、日期、版本、草案、数字、否定词、无答案和 OCR 异常。
7. 样本通过后再导入全部国家级资料，然后决定是否需要向量召回。
8. 后续再增加版本关系、条款对齐、确定性文本 Diff 和省级资料。

## Concrete implementation steps

整个实现拆成可审查的小改动。每一步都有明确输入、可以脱离模型检查的产物，以及聚焦的验证方式。完成第 8 步后即可得到第一个可用路径；后续步骤只在证据链稳定后增加召回和时序推理。

### Step 1: 创建功能分支和包边界

从干净的 Harness 检出创建功能分支。在增加源码前，先阅读包生成和包约束规则，选择一个承载法规能力的新包。该包与 `core/agent-loop`、`web-search-*` 和 Session 持久化保持独立。在设计文档中记录资料根目录、生成索引根目录和运行 profile，再开始实现。

**产物：** 包骨架、README 范围说明、用于配置资料根目录的类型，以及不包含原始资料的首个提交。

**验收：** 包元数据和 workspace 约束通过；缺少资料根目录时能够明确报告配置错误，而不是静默跳过。

### Step 2: 建立原始资料清单

编写离线清单命令，扫描配置的国家级目录中的 `full.md`。每个文件记录来源路径、存在时对应的 PDF 和解析目录、字节长度、SHA-256 哈希、识别到的前几个标题以及稳定的来源 ID。不能从目录名直接推断法律状态。对于缺少配套文件、内容过短、哈希重复或疑似 OCR 失败的文件，标记异常。

**产物：** 清单数据结构，以及 JSON 或 CSV 质量报告，确认 494 份输入文档并列出所有例外。

**验收：** 连续运行两次产生相同的 ID 和数量；只改变资料根目录配置不会改变未变化内容的来源 ID。

### Step 3: 实现确定性的 Markdown 结构解析

解析标题、条、款、项、段落、列表项、表格、附件和原文行号范围，不改写原始文本。识别 `第一章`、`第一节`、`第一条`、中文编号段落和数字列表等常见法规结构。同时支持没有条款编号的规划、通知等文件。无法匹配法律结构的文本保存在通用 `content_unit` 中。

**产物：** 包含父子关系、章节路径、编号、原文行号、文本哈希和解析质量代码的解析记录。

**验收：** fixture 覆盖带发布令的法律、多版本法律、规划、带附件的通知、表格和 OCR 异常；每个 fixture 都能回到原始文本和正确行号。

### Step 4: 抽取文档和版本元数据

抽取候选标题、文件类型、发布机关、适用地域、文号、发布日期、生效起始日期、生效终止日期、修订表述、草案状态和引用文件。每个值同时记录抽取方法和置信度。正文中的明确内容优先于路径线索，二者冲突时都保留。人工审核记录负责解决冲突，自动抽取不能覆盖已经审核的值。

**产物：** 规范化的 `regulation` 和 `regulation_version` 记录，以及缺失或冲突元数据的审核队列。

**验收：** 测试能够区分发布日期、生效日期、规划期限和修订日期；缺少生效日期的来源保持未确定，不能被标成当前有效。

### Step 5: 生成并审核 description

只有在原始清单和文档元数据存在后才生成 description。将完整 Markdown 或有边界的证据块交给模型，并要求返回包含摘要和来源行号的 JSON。由本地导入器保存权威 Markdown，模型不得返回或替代正文。保存提示词版本、模型标识、来源哈希、生成时间和审核状态。

**产物：** 每个文档版本一条 description，状态为 `generated`、`reviewed`、`stale` 或 `rejected`。

**验收：** 法律、规划、标准、通知和废止公告的摘要都保留适用范围和语气强度；来源哈希变化会使旧摘要失效；摘要不能改变时间状态字段。

### Step 6: 建立 SQLite 数据库和可重建索引

建立来源、法规、版本、内容单元、关系、摘要和审核记录表。为规范化标题、别名、文号、标准号、条款编号和日期建立精确索引。对标题、摘要、章节路径、编号和正文建立全文索引。数据库创建放在离线命令中，运行时插件只打开准备好的索引。

**产物：** Schema 版本、可删除重建数据库的导入命令，以及包含语料哈希、Schema 版本和构建时间的索引清单。

**验收：** 相同资料重建后产生相同的逻辑记录和检索结果；数据库不进入 Git；Schema 版本不兼容时明确要求重建。

### Step 7: 实现查询规划器和证据包

将用户问题解析为显式过滤条件和自由文本。先解析明确的名称、文号、条款号、日期和版本比较意图；再按地域、文件类型、审核状态和已核验时间事实过滤；随后进行精确匹配和全文召回，必要时增加 description 召回。返回有边界的证据包，包含稳定结果 ID、原文、来源位置、版本日期、状态、审核状态和匹配原因。

**产物：** 纯查询服务 API，以及精确查询、主题查询、日期查询、历史版本、草案和无答案问题的 fixture。

**验收：** 每个 fixture 都断言选中的来源、内容单元 ID、时间状态和证据文本；时间状态未确定的结果不能以“已确认当前有效”结果出现。

### Step 8: 注册 Harness 服务和工具

增加知识服务提供方和面向模型的 `policy_search` 工具。只有搜索结果需要完整正文或更多来源行号时，才增加 `policy_get_evidence`。使用 `defineTool` 声明有边界的参数、规范 JSON 输出、通过执行信号响应取消，以及索引缺失或资料根目录不可用时的结构化错误。注册提示词段，说明何时检索、如何引用证据以及如何表达不确定性。

**产物：** 能够挂载服务、工具和提示词段的 Cordis 组合，以及不改变标准 preset 的环境法规 Agent preset。

**验收：** 工具调用出现在 Session 日志中并可重放；插件释放后工具注销；只有启用对应组合时，标准 Agent 才能看到法规工具。

### Step 9: 在增加向量检索前建立评测集

建立 80～150 个经过人工核对的问题和期望证据 ID，覆盖明确条款、口语化描述、文号、修订前后日期、废止文件、草案、数字、否定词、只有附件的来源、OCR 错误和无答案问题。分别评估证据召回和回答忠实度。

**产物：** 可重放的检索 fixture，以及能够区分解析、元数据、过滤、排序和回答生成错误的报告。

**验收：** 固定索引下报告结果确定；每个期望答案引用证据 ID，而不是只保存自由文本答案。

### Step 10: 只有评测证明需要时才增加向量检索

如果词法和结构化检索遗漏大量改写问题，再在同一查询服务后增加 Embedding 提供方。对内容单元和可选的 description 建立向量，记录 Embedding 模型和语料哈希，只把向量结果作为候选补充。向量召回后再次执行精确字段和时间检查。向量生成保持离线，提供方可替换；第一版部署不依赖托管向量服务。

**产物：** 混合排序器，以及相对于词法基线的评测对比。

**验收：** 向量检索提高召回率，同时不把错误日期、条款号、数值限制或草案/现行版本混入已接受证据。

### Step 11: 基础问答稳定后增加版本关系和比较

用关系表表示修订、替代、废止、引用、重新编号、拆分和合并。结合结构、编号、词汇相似度和数字比较生成候选关系，低置信度边进入审核。先由程序计算结构和文本 Diff，再让模型只根据已提供的 Diff 和原文总结。

**产物：** `policy_compare_versions` 工具和可审核的关系队列。

**验收：** 每个变化都指向旧、新内容单元；没有存储证据时，模型不能创建关系结论。

### Step 12: 全量导入、发布检查和更新流程

样本语料和评测通过后导入全部 494 份文档。索引清单和质量报告放在本地运行配置旁边，不提交到 Git。定义更新命令，检测新哈希，只重新处理发生变化的文件，使旧 description 和向量失效，并把未解决元数据留在审核队列。为替换 Agent 使用的索引增加独立发布检查清单。

**产物：** 可重建的国家级语料索引、审核积压队列，以及以后纳入省级资料时可复用的更新流程。

**验收：** 变化来源只更新受影响记录；导入失败不会删除上一个可用索引；Agent 返回的证据包含索引构建标识。

### Git 和验证

实现工作在 `deepseek-harness` 的功能分支上进行。导入和模型、索引和检索、Harness 工具、preset、评测分别形成可审查的提交。原始资料、PDF、生成数据库、凭据和运行日志不得提交。每个阶段执行覆盖改动范围的类型检查、Lint、单元测试、文档检查和 `git diff --check`；面向工具的行为使用聚焦测试和可重放证据 fixture 验证。

## Alternatives considered

### Why not prompt-only retrieval?

只使用提示词无法强制版本过滤、稳定的原文位置和有限证据，也会把无关文档消耗在上下文中。

### Why not vector-only retrieval?

向量相似度不擅长条款号、日期、数字阈值、否定词和法律状态，因此只能作为补充召回，不能作为适用性依据。

### Why not modify the Agent Loop?

这个能力可以由知识服务、工具和 preset 组成。修改 Loop 会扩大维护面，却不能改善法规数据模型。

### Why not deploy a graph and vector database immediately?

当前语料规模适合本地可重建索引。外部数据库会在检索效果尚未测量前增加部署和迁移成本。

## Acceptance criteria

- 导入器可以确定性处理国家级资料，并报告所有未解决或低质量记录。
- 查询可以返回准确的文档、版本、章节、原文、来源位置和时间状态证据。
- 缺少日期或未核验状态不会被转换成“当前有效”的结论。
- 环境法规工具只在对应组合中可用，不改变标准 Agent Loop。
- 固定问题同时评测证据召回和回答忠实度。
- 原始资料和索引可以重建，且不出现在 Git 提交中。

## Risks

OCR 错误、标题歧义、历史版本重复、施行日期缺失和只有附件的文件，都会产生看似合理但错误的回答。摘要可能改善发现能力，也可能引入原文没有的概括。因此，低置信度元数据和关系匹配必须保持可审核。法律回答受本地资料范围和审核状态限制，外部更新必须经过重新导入和审核。
